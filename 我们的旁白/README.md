# 进度旁白（简）

> 模型闷头干活、界面上很久没有正文时，在两步之间插一句话，让它自己说清在做什么 —— **不结束回合，不取消任务**。

这是 `Asza-other/dsh-narrator` 的精简重写版：只保留机制（计时 → 记账 → step 边界注入），
砍掉左下角浮窗、原文截取、自检计数。机制分析、参考对照、踩过的坑见 [ANALYSIS.md](ANALYSIS.md)。

## 它做什么

| | |
| --- | --- |
| 何时算「沉默」 | 距**最后一次正文输出**超过 `silentSeconds`（工具调用、纯思考都不算说话） |
| 什么时候插话 | 到点只记一个标记，真正注入在下一次 `agent/pre-step`（step 边界），不会撞 `tool_calls ↔ tool 结果` 的配对 |
| 注到哪 | 本步的 `decision.messages` 末尾追加一条 `role: 'user'` 消息，`source.form = 'notice'`：不进对话流、不会变成一条假的「用户发言」；宿主把它当 context 节点，界面上只多一行来源标记 `narrator-lite · 要求模型中途汇报进度`，模型按普通上下文读它 |
| 为什么不会打断 | 消息批次非空 → 宿主那条「messages 为空就判定回合结束」的规则判不出结束；提示词末尾还写死「说完继续，不要停下来等确认，也不要重做已完成的部分」 |
| 怎么限流 | `cooldownSeconds`（两次注入最小间隔）+ `maxPerTurn`（单回合上限，0 = 不限） |
| 子代理 | 一律不参与（`session.header.origin === 'subagent'` 判据）——那些会话界面上看不见，注入等于白烧一次调用 |

## 默认值

| 字段 | 默认 | 量程 | 说明 |
| --- | --- | --- | --- |
| `enabled` | `true` | 布尔 | 总开关；设置页关掉后立刻停表 |
| `silentSeconds` | `90` | 10–3600 | 多久没有正文算沉默。低于 10 秒等于每步都插一句 |
| `cooldownSeconds` | `120` | 0–3600 | 两次提醒最小间隔，0 = 不限（**但 `maxPerTurn` 也是 0 时会被抬回 120**） |
| `maxPerTurn` | `4` | 0–50 | 单回合最多提醒几次，0 = 不限 |
| `prompt` | 内置中文文案 | ≤2048 字符 | 想换角度就让模型怎么汇报，只能写在插件配置里 |

> 两个刹车不许同时松开：阈值下限只有 10 秒，`cooldownSeconds` 和 `maxPerTurn` 同时为 0
> 就等于每个 step 边界都往会话里插一句，纯烧 token。真撞上这种组合时冷却会被抬回默认值
> （想完全不限，至少给单回合留一个上限），设置页也会在冷却那一行写明。

设置页可改前三项（开关 / 阈值 / 冷却），存在 `$DSH_HOME/narrator-lite/config.json`；
`prompt` 与 `maxPerTurn` 只在插件配置里改，免得设置页变成一个能往会话里投任意长指令的入口。

### 配置文件读不到 / 读坏了怎么办

覆盖层是「设置页保存的那一层」，读它失败时必须分清两种情况——**不能都当成「没有配置」**，
否则设置页会把默认值当成用户存过的东西画出来，用户一点保存，整份覆盖写就把旧设置永久抹掉：

| 情况 | 处理 | 会不会写盘 |
| --- | --- | --- |
| 文件不存在 | 用默认值，正常可写 | 会 |
| 文件损坏（JSON 解析失败） | 先备份成 `config.json.broken-<YYYYMMDD-HHMMSS>`，再用默认值；设置页顶部提示「已备份为 …」 | 会（坏文件已被保住，写的是全新一份） |
| 读失败（Windows 上 `EBUSY`/`EPERM` 很常见） | 标成「配置不可信」：设置页提示 + 锁住所有控件 + 给一个「重新读取」；**每次请求都会重试**，不是一次性终态 | 不会，POST 直接回 `409 config-unreadable` |

## 装（本仓库只交付源码，未安装）

1. 把整个目录拷进 `<profile>/node_modules/dsh-plugin-narrator-lite`
2. 在该 profile 的 `package.json` 里，`dependencies` 与 `dsh.profile.bundles` **两处**都登记
3. 重启 DSH，设置页里会出现「进度旁白（简）」

## 自检

```bash
node --check lib/index.js && node --check lib/client.js
node --test test/host.test.mjs     # 30 项：计时语义 / 注入位置 / 开关 / 限流 / 淘汰 / 写盘 / 取消 / 覆盖层读失败
node --test test/client.test.mjs   # 12 项：客户端半确实导出 apply + inject，设置页真跑一遍
```

测试用 Node 的 mock timers，不需要真宿主；`DSH_HOME` 会在 import 插件前指到临时目录，
不会读到你真实的用户配置。客户端半那份用 `vm` 把 `lib/client.js` 当浏览器脚本加载，
喂一个假 `ctx`（`effect` / `slots`），所以「设置页注册不上」这类 bug 也能在本地抓到。

## 已知限制

1. **机制不保证模型一定开口**：它只保证回合不被关掉；模型自己写完就停那还是会停，提示词末尾两句是补这个漏。
2. **注入有延迟**：到点只是记账，要等下一个 step 边界；主会话在等子代理时可能等几分钟。
3. **会占上下文**：每条注入都作为 context 节点持久化，所以默认 90 秒阈值 + 120 秒冷却 + 单回合 4 次。
4. **没有浮窗**：不做可视化，界面上看不到「它多久没说话了」；要看进展就靠模型被提醒后说的那段正文。
5. 只支持 web 端；客户端半只注册设置页，失败时只打一条 `console.warn`，不影响宿主半工作。
6. **单步回合拿不到中途提醒**：注入只可能发生在 step 边界，而宿主的 step 从 1 开始数；
   实现里对「本步没有待处理消息」的情况直接放行第 1 步（`step <= 1`），不能把它变成一次新请求。
   所以一个回合如果只有一步、模型在这一步里长时间思考或调工具，中途不会插话——那段时间里
   根本没有 step 边界可用。这时这次提醒就作废，下一个回合重新计时。这是刻意保留的例外，
   不是漏判。
7. **会话淘汰用的是「最后一次活动」，不是「最后一次正文」**（工具调用、思考、step 边界的帧都算），
   但长工具执行期间这几类帧都没有——理论上仍可能在一个很忙的机器上被当成最不活跃的那个淘汰掉。
   要撞上得同时有 32 个以上活跃会话且其中一个卡在几分钟以上的工具里；真遇到了再说，不为此加机制。
